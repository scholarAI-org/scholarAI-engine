# ScholarAI-engine

# نظام استخراج معايير الأهلية للمنح الدراسية — Scholar AI

توثيق كامل لمسار بناء pipeline استخراج 11 حقل أهلية من وصف كل منحة (~384 منحة)، باستخدام نماذج Groq، مع تفصيل كل خطأ واجهناه وسبب حدوثه وطريقة الحل.

---

## 1) الهدف من النظام

استخراج الحقول التالية من `description` كل منحة (نص عربي حر غير موحد البنية):

```
allowed_nationalities, target_degree_levels, allowed_gender,
target_residencies, min_gpa_percentage, max_age,
allowed_fields_of_study, requires_english_proof, funding_type,
is_req_experience, is_Softskills_required
```

`id`, `title`, `deadline` تُؤخذ مباشرة من الـ endpoint ولا تُستخرج بالنموذج.

---

## 2) البنية العامة للـ Pipeline

```
1. جلب البيانات من REST endpoint (id, title, description, deadline)
2. تنظيف + استخراج الأقسام المفيدة من description (section_extractor.py)
3. إرسال النص المنظف لنموذج أساسي (Primary Model) بطلب JSON مجبر
4. عند فشل النموذج الأساسي بعد محاولات retry → انتقال صامت لنموذج بديل (Fallback Model)
5. حفظ النتائج تدريجياً (incremental) بملف JSON بعد كل نتيجة
6. عند الحاجة: إعادة معالجة الفاشلين فقط (retry_failed_only / run_remaining_and_retry)
```

**مبدأ التصميم الأساسي:** كل شيء flat functions (بدون classes)، حفظ incremental دائم لتفادي فقدان العمل عند أي انقطاع.

---

## 3) الملفات الناتجة من الجلسة

| الملف | الوظيفة |
|---|---|
| `Extract_Fields.py` | الملف الرئيسي: جلب البيانات، الاستدعاءات المتوازية، الحفظ |
| `section_extractor.py` | استخراج أقسام (المراحل الدراسية / التخصصات / شروط التقديم) من النص الخام بـ regex |
| `compact_json_writer.py` | حفظ JSON بتنسيق مقروء (قوائم بسطر واحد، كائنات مفرودة) |
| `scholarships_raw.json` |( البيانات المستخرجة من endpoint ) |
|Answer.json|( correct result from gemini req directly ) 
|Final_scholars_extraction.json| final result of in the latest run attempts

## 5) الأخطاء التي ظهرت، سببها، وطريقة الحل

### 5.1 — JSON فارغ أو مقطوع (`Expecting value: line 1 column 1`)

**السبب:** نموذج reasoning (`gpt-oss-120b`) يستهلك `max_tokens` بالتفكير الداخلي قبل ما يطلع أي حرف من الـ JSON، فينقطع أو يرجع فاضي.

**الحل:**
- `reasoning_effort="low"` بدل القيمة الافتراضية (تقليل التفكير الداخلي).
- رفع `max_tokens` لهامش كافٍ (1500–2000).
- إجبار `response_format={"type": "json_object"}` على مستوى الـ API نفسه.

---

### 5.2 — Rate Limit على مستوى الدقيقة (`429 — tokens per minute (TPM)`)

**السبب:** إرسال طلبات متزامنة كثيرة (concurrency عالي) يستهلك كل الحصة المتاحة بالدقيقة (TPM) بسرعة.

**الحل:**
- تقليل `Semaphore` (من 5 إلى 3 ثم لاحقاً لـ 3-4 حسب الموديل).
- **Retry مع قراءة وقت الانتظار الفعلي من رسالة الخطأ نفسها** (`"try again in Xs"`) بدل تخمين وقت ثابت:

```python
match = re.search(r"try again in ([\d.]+)s", error_str)
wait_time = float(match.group(1)) + 0.5 if match else 5 * (attempt + 1)
```

---

### 5.3 — Rate Limit على مستوى اليوم (`429 — tokens per day (TPD)`)

**السبب:** كل نموذج عنده حصة يومية منفصلة (TPD)، تُستهلك من كل التجارب المتراكمة باليوم (بما فيها الاختبارات الصغيرة)، وتتصفر مرة واحدة فقط عند **00:00 UTC**.

**كيف يُكتشف:** صفحة Groq Console → **Usage → تبويب Activity** (وليس Cost) تعرض توكنز Cached/Uncached Input وOutput الفعلية لكل يوم — هذا الرقم الموثوق الوحيد، وليس عدد الـ API Calls.

**الحل:**
- توزيع الحمل بين نموذجين (Primary + Fallback) لهما TPD منفصل تماماً.
- تفادي تكرار التجارب الاستكشافية على النموذج الأساسي وقت الضغط، والانتقال للفallback بدل الانتظار.

---

### 5.4 — نموذج Fallback متوقف (`model_used = None` لكل المحاولات)

**السبب:** `llama-3.3-70b-versatile` تم إيقافه (decommissioned) من Groq بتاريخ 16 أغسطس 2026. أي استدعاء له يفشل فوراً، فتفشل كل من المحاولة الأساسية والبديلة معاً.

**الحل:** التأكد من قائمة الموديلات المتاحة فعلياً بصفحة Groq Console بدل الاعتماد على اسم موديل من الذاكرة، واستبداله بموديل نشط (`openai/gpt-oss-20b`).

**درس عام:** أي "fallback" لازم يُختبر لحاله على عينة صغيرة قبل الاعتماد عليه بمعالجة كاملة — موديل غير مُتحقق منه قد يفشل بصمت ويُفقد بيانات (كان `model_used=None` بدون بيانات مستخرجة لعدة منح قبل ما ننتبه).

---

### 5.5 — Rate Limit خاص بالمخرجات (`429 — Output Tokens Per Minute (OTPM)`)

**السبب:** بعض الموديلات (مثل `qwen3.6-27b`) لها حد منفصل تماماً على توكنز **المخرجات فقط** بالدقيقة (غير TPM العادي)، منخفض نسبياً (1000). أي `max_tokens` أكبر من هذا الحد يفشل الطلب فوراً بغض النظر عن التزاحم.

**الحل:** ضبط `max_tokens` لكل موديل بشكل منفصل حسب حدوده الخاصة، بدل استخدام نفس القيمة لكل الموديلات.

---

### 5.6 — موديل Preview غير مناسب للإنتاج (`qwen/qwen3.6-27b`)

**الدرس:** موديلات مصنّفة "preview/experimental" على Groq:
- موجهة أساساً لتقييم قدرات جديدة (وأحياناً focus مختلف مثل الصور)، وليست للاستخدام بمعالجة إنتاجية مستقرة.
- إحصائيات استخدامها قد لا تظهر بشكل طبيعي بلوحة Usage.

**القرار:** تفضيل موديل نصي مستقر (`gpt-oss-20b`) كـ fallback بدل موديل preview، حتى لو الأخير "أذكى" نظرياً بمقاييس عامة.

---

### 5.7 — أخطاء متنوعة غير مغطاة بالـ Retry (`Connection error.` / `json_validate_failed`)

**السبب:** شرط الـ retry الأولي كان يغطي فقط `"429"` و`"timeout"` بنص رسالة الخطأ. أخطاء أخرى (انقطاع اتصال لحظي، أو رفض الموديل توليد JSON صالح لأسباب داخلية عرضية) كانت تُسجَّل كفشل نهائي فوراً بدون أي محاولة إعادة.

**الحل:** تبسيط شرط الدخول للـ retry ليشمل **أي خطأ** بدل تحديد أنواع معينة:

```python
if attempt < max_retries - 1:   # بدل: if (is_rate_limit or is_timeout) and ...
```

**درس عام:** فحص محتوى `'failed_generation'` بالخطأ ضروري لتشخيص هل السبب هو "قلة توكنز" (نص مقطوع) أو "فشل توليد عرضي" (نص فارغ تماماً) — الحالتان لهما نفس كود الخطأ لكن أسباب مختلفة.

---

### 5.8 — استخراج ناقص لمنح ذات بنية غير قياسية (منح إيطاليا وغيرها)

**السبب الأول (سطحي):** بعض المنح تضع معلومات جوهرية (المراحل الدراسية، التخصصات) بأقسام منفصلة تماماً عن "شروط التقديم"، فالقص الأولي (بحدود ثابتة start/end) كان يفوّتها بالكامل.

**الحل:** الانتقال من "قص بين نقطتين ثابتتين" إلى **دالة تبحث عن أي عنوان من قائمة عناوين معروفة، وتقص من بعده لحد أقرب عنوان تالٍ** (بغض النظر عن ترتيب الأقسام بالنص) — `section_extractor.py`.

**السبب الثاني (أعمق، اكتُشف لاحقاً):** بعض العبارات المستخدمة كـ"ماركرات" (مثل "المرحلة الدراسية" أو "التخصصات الأكثر طلب") تتطابق أحياناً **كعبارة عرضية وسط جملة عادية**، وليس فقط كعنوان قسم حقيقي (مثال: *"...تختلف نسبة التغطية وفقًا للبرنامج والمرحلة الدراسية"*). هذا كان يفتح حدود قسم وهمية ويسحب محتوى غير ذي صلة (رسوم، مواعيد رد) لقسم خاطئ، وأحياناً يُنتج تكرارًا فعليًا في النص المُجمَّع.

**الحل النهائي:** اعتبار أي تطابق نصي "عنوان قسم" فقط إذا كان يقع **ببداية سطر مستقل** (مسبوق مباشرة بـ `\n` أو ببداية النص):

```python
def is_line_start(text, pos):
    line_start = text.rfind("\n", 0, pos) + 1
    prefix = text[line_start:pos]
    return prefix.strip() == ""
```

**درس عام:** أي نظام يعتمد على "كلمات مفتاحية" لتحديد بنية نص حر معرّض دائمًا لتطابقات كاذبة وسط الجمل. اشتراط موقع العبارة (بداية سطر) يقلل هذا الخطر بشكل كبير دون تعقيد الكود.

---

### 5.9 — تنسيق حفظ JSON غير مقروء (Lists مفرودة بعدة أسطر)

**السبب:** `json.dump(..., indent=2)` يفرد كل عنصر بأي قائمة (list) بسطر مستقل، مما يجعل الملف طويلاً وصعب المسح البصري.

**نقطة تقنية مهمة:** طلب من النموذج (بالـ prompt) إخراج القوائم مضغوطة **لا يحل المشكلة**، لأن التنسيق النهائي بالملف يتحدد وقت الحفظ (`json.dump`) وليس بشكل رد النموذج الخام — بمجرد تحويل الرد لـ Python dict عبر `json.loads()`، يضيع شكل التنسيق الأصلي تمامًا.

**الحل:** دالة حفظ مخصصة (`compact_json_writer.py`) تفرد الكائنات (dicts) لكن تُبقي القوائم (lists) بسطر واحد مضغوط.

---

## 6) دروس عامة للمستقبل (تنطبق على أي مهمة استخراج مشابهة)

1. **لا تعتمدي على الذاكرة/الافتراضات لأسماء الموديلات أو حدودها** — تتغير بشكل متكرر (تم إيقاف موديل بالكامل خلال شهر واحد). تحققي دائمًا من Console مباشرة.
2. **افحصي `Usage → Activity` (توكنز فعلية) لا `Cost` (دولار) ولا عدد الطلبات** عند تشخيص مشاكل الحصص.
3. **كل موديل fallback يحتاج اختبارًا منفصلًا على عينة صغيرة** قبل الاعتماد عليه على نطاق واسع — قد يفشل بصمت أو يعطي جودة أقل دون تحذير واضح.
4. **الـ retry الأعمّ (أي خطأ) أفضل من الـ retry الانتقائي** إلا إذا كان هناك سبب واضح لتفرقة السلوك (مثل انتظار وقت مختلف).
5. **الحفظ التدريجي (incremental) إلزامي** في أي معالجة تستغرق وقتًا طويلاً — لا توكنز ولا نتائج تضيع عند أي انقطاع (يدوي أو بسبب خطأ).
6. **regex على نص حر دائمًا معرّض لتطابقات كاذبة** — اشتراط موقع العبارة (بداية سطر/فقرة) خط دفاع بسيط وفعال.
7. **تنسيق ملف الإخراج يُضبط وقت الحفظ، وليس عبر الـ prompt.**

## 7) حالة المشروع عند نهاية الجلسة

- استخراج الحقول الـ11 لمعظم الـ384 منحة عبر Primary + Fallback مع retry شامل.
- تحسين استخراج الأقسام (المراحل/التخصصات/الشروط) ليعمل بشكل عام دون الاعتماد على ترتيب ثابت.
- إصلاح تطابقات كاذبة بالـ regex عبر اشتراط بداية السطر.
- توحيد تنسيق ملف الإخراج (قوائم مضغوطة).
- بناء نواة أولية لمحرك التوصية (`recommendation_core.py`) بفلاتر صارمة (nationality, residency, gender, degree, gpa, age, experience) وترتيب اختياري (field match, funding, soft skills, english proof).

**التالي المقترح:** تشغيل الدفعة الكاملة بالإعدادات النهائية، مراجعة عينة عشوائية من النتائج يدويًا للتأكد من الجودة، ثم دمج `recommendation_core.py` مع `semantic_matcher.py` الموجود لتحسين مطابقة التخصصات النصية الحرة.
